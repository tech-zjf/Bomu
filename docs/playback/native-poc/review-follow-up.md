# 第一轮审查跟进

本次保留既有模块划分，聚焦测量可信度、暂停命令确认与视频调度。v0.0 仍未完成全部验收。

## 暂停命令与交错快照

修复前新增 `testStalePauseSnapshotCannotAcknowledgeNewerIntent`，稳定复现了两个断言失败：用户依次暂停、播放，再收到“操作前的播放快照”和“第一次暂停的快照”，界面会退回暂停，第三次点击错误地发送播放。实际命令序列为 `[true, false, false]`，预期为 `[true, false, true]`。

原因是旧实现仅按暂停布尔值相等解除待确认意图，无法区分相同状态来自哪一次操作。现在 `PlaybackPauseRequest` 包含文件 `requestID`、递增 `commandID` 和目标值；控制队列完成属性设置后才把编号带入采样结果。模型只由对应编号确认意图，状态层拒绝已经确认过的编号之前的快照。切文件重置原生确认编号并拒绝旧文件命令，终态与退出清除待确认意图。

修复后的同一交错用例继续检查确认后迟到的旧状态；真实内核测试检查编号返回、切文件重置及旧命令拒绝。运行记录：`.build/test-pause-interleaving-before.log`（1 个测试、2 个断言失败），`.build/test-pause-interleaving-after.log`（10 个测试通过）。

所有调整后的最终 `build-dev.sh` 与 `test-dev.sh` 通过，10 项回归、0 失败、约 3.04 秒；日志为 `.build/build-review-final.log` 和 `.build/test-review-final.log`。

随后重新启动正式 Bomu，打开用户指定原视频，实际画面正常；连续执行暂停/播放/暂停后，界面和进度停在约 4.75 秒。该人工操作补充产品入口证据，确定性交错时序仍由上面的回归测试覆盖。

## CPU 与原生资源证据

CPU 使用 `getrusage` 的秒/微秒，不再把 `proc_pid_rusage` 的 Mach 时间值直接当纳秒。第一轮的 0.19% 不用于验收。17:25:58 开始的独立 AppKit 基准为此前已通过的可信记录，详见 [benchmark.md](benchmark.md)；它记录了全部可见采样、真实帧提交、停止后计数不再增长，以及销毁后 core/render context 标记释放。

这些标记在原生所有者执行释放后采样；它们证明对应资源所有权已结束，不单独证明所有系统缓存回收或长期无泄漏。

## 时序测量口径

新诊断记录有效媒体帧完成 `glFlush` 时，相对 mpv `target_time` 的差值。负值是提前提交，正值是延迟提交。计数排除旧帧重绘和重复帧；早于目标超过 2 ms 单独计数，未提供目标时间时保持未知。

固定 mpv 0.41.0 的 `render.h` 注释仍写微秒，但 [vo_libmpv.c](https://github.com/mpv-player/mpv/blob/v0.41.0/video/out/vo_libmpv.c#L423) 直接返回 `vo_frame.pts`，[vo.h](https://github.com/mpv-player/mpv/blob/v0.41.0/video/out/vo.h#L213) 将其定义为纳秒，[client.c](https://github.com/mpv-player/mpv/blob/v0.41.0/player/client.c#L1991) 提供同源纳秒时钟。因此测量显式使用该固定版本的纳秒合同，再转成微秒累计，不根据数值大小猜单位。升级依赖时必须重新核对该边界。`.build/benchmarks/20261013-173912/` 是使用过时注释单位的无效诊断，已排除。

提交时间不等于 GPU 完成、屏幕出光或扬声器出声。即使消除了提前提交，也不能据此宣布物理音画同步通过。

## 调度修复与重测

原先的 render 调用禁用目标时间等待，但核心仍使用默认 `video-timing-offset=0.05`。现在按 [render API 的零提前量方案](https://github.com/mpv-player/mpv/blob/v0.41.0/include/mpv/render.h#L300)，将核心配置为 `video-sync=audio`、`video-timing-offset=0`；可见绘制与隐藏跳帧都不在持锁期间等待未来目标。让 mpv 在音频时钟目标到期时交付帧，避免重复建设定时器或在 AppKit 主线程睡眠。

同机调度修复前后均完整跑过独立基准，原始来源与当前源码哈希已归档在 [本轮基线](baseline-2026-10-13-after-review.json)。表中均值通过阶段前后累计数相减，只统计稳定播放阶段。

## 同步素材与尚需采集的证据

运行 `python3 scripts/generate-sync-fixture.py` 生成 `.build/sync-fixture/av-sync-1080p60.mov`：1080p、60 fps、H.264 + 48 kHz PCM，30 秒；每隔两秒显示 100 ms 白色方块并输出 100 ms、1 kHz 短音，共 15 次。

生成后解码视频中心像素和实际 PCM，确认所有闪光/声音起点。当前文件最大源偏差约 0.0208 ms（一个音频样本）；manifest 记录每次起点、许可来源、文件哈希和真实媒体属性。素材不写入版本控制。

物理端到端同步仍需用带共同时间基准的屏幕/扬声器测量设备或外部拍摄，覆盖长时间播放、暂停恢复、定位、窗口变化与不同输出设备。单张截图、主观“声音正常”、内核进度以及源素材自身对齐均不能替代这项证据。

## 全量审查后的修复

本轮修复连续定位丢失、未声明的 Python 3.11 依赖、窗口基准遗漏采样间遮挡三个问题，并统一定位能力判断、给逻辑测试等待加上超时、为原生测试加入素材完整性校验。保留现有模块和资源归属，没有引入新的框架或额外播放状态事实源。

原定位实现用最新快照的位置相加，在快照仍为 30 秒时连续输入 `+10、+10、−10`，会发出 `40、40、20` 三个绝对目标。现在 `PlaybackSeekRequest` 显式表达相对/绝对定位及文件请求，适配层在当前文件的控制队列中提交；[固定 mpv 的定位队列](https://github.com/mpv-player/mpv/blob/v0.41.0/player/playloop.c#L422) 已具备累计和合并语义。原生回归在暂停状态先定位到 3 秒，再连续提交 `+2、+2、−1`，确认落在 6 秒；连续提交绝对 9 秒、相对 −2 和 +1，确认落在 8 秒。切文件后旧请求的绝对与相对定位都不改变新文件。界面仍只把内核快照当成实际播放位置。

素材校验统一使用 Python 3.9 可用的分块 SHA-256；现有 8 个本地素材全部通过系统 Python 3.9.6 校验。原生测试脚本与 Xcode 复制素材阶段均会检查哈希，文件变化或缺失明确失败，不只检查 manifest 存在。验证过程未改动用户视频或重新生成现有素材。

窗口报告升级为 schema 3，在持续播放区间监听 AppKit 的遮挡状态变化，记录变化时间及观察结束时间。短暂遮挡后恢复仍保留中断，汇总程序也会拒绝中断或未结束的观察记录。schema 1/2 历史报告保持原始内容，文档与新汇总明确限定为采样点可见；不能据此证明此前整个区间均未遮挡。
