# Library 时长排序

## 用例与事实边界

用户在 Library 选择 `Sort → Duration` 时，当前分类与观看状态筛选下的媒体按真实时长从短到长排列。时长由本地 AVFoundation 属性探测提供；不能读取的文件和离线文件保持未知并排在末尾。同一时长与未知项按媒体 ID 稳定排序。排序不会写入原视频或向数据库加入派生属性；媒体库数据库继续只保存可恢复的用户事实。

## 调用链与生命周期

`MediaLibraryView` 的排序和筛选状态决定探测范围，并用绑定到 Library 页面、排序、筛选和库快照代次的 SwiftUI task 持有探测。`MediaLibraryModel.loadDurationsForSort` 最多同时提交两个探测；`MediaMetadataProbe` 复用可见卡片的同内容请求和共享 `AsyncPermitPool`。播放期间预算收紧为一个后台媒体工作。探测结果只在媒体 ID 与内容版本仍匹配、时长有限且非负时进入本次应用会话的 `durationFacts`；每 16 项发布一次进度与排序更新。切换页面、排序或筛选会取消上一轮 task，底层探测按已有取消合同释放资源；旧轮次不能清除新轮次的进度。

卡片本来就需要按需探测元数据；成功读到真实时长时也可填充同一会话的时长事实。当前不会为全库提前探测，也不会跨应用启动持久化派生时长。首次对大型库选择 Duration 可能耗时，页面显示已测数量；无法得到真实时长的条目持续显示在末尾。换筛选或重新启动后，仅本会话已取得的时长可立即复用，其余按需重新探测。这是当前 v0.0 的性能与数据边界，不能将进度或未知值解释为完整时长事实。

## 验证

- `./scripts/test-dev.sh --direct-hostless`：154 项 Python、205 项 XCTest（2 项 APFS 专项按默认入口跳过），0 失败。新增行为回归覆盖真实库条目的探测与升序、未知/旧内容版本靠后、共享并发预算和离开排序后的取消。
- `./scripts/build-dev.sh --analyze -quiet` 与 `./scripts/build-dev.sh -quiet` 通过；规范 Debug 包身份源码摘要 `6452a93d952d52f7e6828b2f793ba036870779817b42454646b080ad93f5ce5f`，启动前 `verify` 通过。
- 在该包的一个普通窗口中，Library 菜单显示 Duration；30 项许可媒体库的已知 5 秒、6 秒、30 秒样片顺序与升序一致，末尾显示离线/无效/无法探测时长条目。页面显示“Media with unknown duration appears last.”。同一包在当前屏幕精确 `960×640 pt` 的窗口中复核了 Duration 选项、前三张卡片的 `0:05`、`0:05`、`0:06` 次序和状态文案，未见控件/卡片明显重叠。结束前恢复 Recently Added 与原窗口尺寸，并确认验收进程退出。

可见检查证明当前样本和窗口交互，未测 10,000 项首次完整探测耗时、长时间连续滚动帧率或真实播放时同时排序的运行负载；这些仍归入 v0.0 性能验收。
