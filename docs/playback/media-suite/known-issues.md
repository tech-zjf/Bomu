# 未关闭的兼容性问题

## MPEG-TS 中途精确定位没有恢复视频帧

优先级：P2；状态：已定位至 MPEG-TS 解封装层，候选修正通过独立内核回归，尚未接入正式运行库。素材为测试包中的 `20-h264-aac.ts`，正常解码通过，预期仍为可播放文件，不改成预期失败。

复现步骤：打开文件，等待实际播放，暂停，定位到约 3 秒，再恢复。播放器的原生位置断言通过，但之后没有新视频帧，直到文件结束。H.264 MP4 等其他用例的相同步骤通过；切换到下一个文件能恢复播放。

该片约 6 秒，只有起始处一个视频关键帧。早期独立 FFmpeg 对原文件进行输入定位（`-ss 3 -i`）后没有输出视频帧；从头解码后再截取（`-i … -ss 3`）可以输出 90 帧。这提供了素材可完整解码、故障发生在定位路径的独立证据。原生报告保留了该项的请求、定位目标、帧计数与失败结果；具体原因由后续源码和重编对照进一步确认。

[mpv 官方定位说明](https://mpv.io/manual/stable/#options-hr-seek-demuxer-offset) 提及部分解复用器无法准确回到目标前的关键帧，并说明时间偏移绕过会增加解码开销。本轮没有为该样本添加偏移常量、文件名判断、转码或隐式重新打开策略。

后续对照已完成：相同编码负载换成 MP4/MKV 后定位正常；固定内核和同参数重编的未修改 FFmpeg 都复现 TS 故障。仅修正 `mpegts_get_dts` 的视频定位点与关键帧索引后，短片、长片、H.264、H.265 Main10、MPEG-2 与纯音频对照通过。15 分钟文件的 3 个定位目标也恢复到了目标附近并连续输出新帧。全过程使用原有 libmpv、解码库与内存软件渲染，未修改 Bomu 的 UI 或播放状态模型。

增加缓存只能让完整缓存的短片避开错误；长片跳到缓存外仍错误地落到后一个关键帧，不能据此关闭问题。完整设计、来源、取舍与测量边界见 [定位调查](seek-investigation.md)，可重跑工具见 [SeekProbe](../../../Tools/SeekProbe/README.md)。

下一步是候选运行库的单窗口 OpenGL/A04 验证，以及连续定位、取消和快速切文件回归；随后才能决定运行库接入与版本固定。本轮桌面锁屏，尚未执行候选内核的可见测试。正式应用仍使用原始固定运行库，A04 仍为 29/30；不把实验成功写成正式应用已修复。
