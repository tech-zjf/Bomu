# 未关闭的兼容性问题

## MPEG-TS 中途精确定位没有恢复视频帧

优先级：P2；状态：已稳定复现，尚未修复。素材为测试包中的 `20-h264-aac.ts`，正常解码通过，预期仍为可播放文件，不改成预期失败。

复现步骤：打开文件，等待实际播放，暂停，定位到约 3 秒，再恢复。播放器的原生位置断言通过，但之后没有新视频帧，直到文件结束。H.264 MP4 等其他用例的相同步骤通过；切换到下一个文件能恢复播放。

该片约 6 秒，只有起始处一个视频关键帧。独立 FFmpeg 对原文件进行输入定位（`-ss 3 -i`）后没有输出视频帧；从头解码后再截取（`-i … -ss 3`）可以输出 90 帧。这说明素材可完整解码，并提供了低层容器定位问题的独立证据；尚不能据此声称已定位到 mpv/FFmpeg 的某个具体函数或完成修复。原生报告保留了该项的请求、定位目标、帧计数与失败结果。

[mpv 官方定位说明](https://mpv.io/manual/stable/#options-hr-seek-demuxer-offset) 提及部分解复用器无法准确回到目标前的关键帧，并说明时间偏移绕过会增加解码开销。本轮没有为该样本添加偏移常量、文件名判断、转码或隐式重新打开策略。

下一步先用相同编码负载的不同容器作对照，确认索引/回溯行为及大文件开销，再设计定位完成与失败的契约。完成条件应包括实际音视频恢复，不能只看 `time-pos` 已改变或 `isSeeking=false`；需要覆盖暂停中定位、连续定位、取消和快速切文件。

第一次参数回归没有识别这个缺陷：`vo-configured=false`、音频输出正常，并不等于 CAOpenGLLayer 的上一纹理已经消失。随后实际观察窗口，确认切到纯音频仍显示上一视频。

修复使用原生视频输出状态驱动渲染层清屏，不在 SwiftUI 添加遮罩。回归增加 clear-only 绘制状态和清屏计数，并实际观察纯音频黑色背景及切回视频后的画面。最终验证结果见 [validation.md](validation.md)；修复前参数用例“通过”不能追溯解释为当时画面已正常。
