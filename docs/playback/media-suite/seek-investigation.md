# MPEG-TS 精确定位调查与候选修正

日期：2026-10-13。状态：**独立内核候选与交错操作回归已验证，正式应用尚未修复**。固定运行库与 `Config/Dependencies.lock.json` 保持原样，A04 的应用验收仍是 29/30。

后续已补齐播放用解封装配置，通过清单/符号核验、含压缩 MOV 的 9 组回归和独立重复构建，新的候选应用已准备但未启动，见 [runtime-candidate.md](runtime-candidate.md)。下文保留首次最小配置调查的原始结果。

## 问题与原因

原始 6 秒 H.264/AAC TS 可以从头解码，但暂停后精确定位到 3 秒只恢复音频时钟，没有新视频帧。把同一编码负载重封装成 MP4、MKV，三者完整解码的视频 SHA-256 相同，MP4/MKV 的同一操作正常。这将故障缩小到容器解封装定位路径。

mpv 0.41.0 的 [`demux_seek_lavf`](https://github.com/mpv-player/mpv/blob/v0.41.0/demux/demux_lavf.c) 调用 FFmpeg 的 `av_seek_frame`。FFmpeg 9.0.1 的 [`mpegts_get_dts`](https://github.com/FFmpeg/FFmpeg/blob/n9.0.1/libavformat/mpegts.c) 在搜索时间戳时，把遇到的包统一写为 `AVINDEX_KEYFRAME`，并可返回非关键视频包的位置。返回时间点并不等于返回可独立解码的起点：没有后续关键帧的短片可能直接视频 EOF，长片则可能落到目标之后的关键帧。

修正位于这个解封装边界：视频只把 `AV_PKT_FLAG_KEY` 包当作可用定位点，并为索引保存真实的关键帧语义；音频和 raw TS 数据流保留原有按包定位语义。没有按文件名、扩展名或样本 ID 修改应用行为，也没有改变 UI、重复打开文件或转码播放。

这已超出“从日志推测”：同参数重编、未修改的解封装库仍复现原问题；只加入上述修正后，候选恢复正确位置和实际新帧。修改仍是本地候选，未向上游提交，不能据此宣称所有 TS、开放 GOP、多节目流、交错视频或损坏流均已兼容。

## 对照构建与资源归属

工具入口是 [SeekProbe](../../../Tools/SeekProbe/README.md)，调用链见 [flow.md](flow.md#ts-定位的独立内核对照)。

- 原版运行库：仓库固定的 mpv 0.41.0 / FFmpeg 9.0.1，使用现有依赖校验。
- 源码：官方 `ffmpeg-9.0.1.tar.xz`，SHA-256 为 `cf38e0e28c7e5605942c4a77755349b0145804a397af37eb1fb4c77cb237f635`。
- `rebuilt` / `candidate` 使用同一源码、工具链和构建参数，只有候选源文件有关键帧语义修正。两个独立运行库仅替换各自目录中的 `libavformat.63.dylib`，其余动态库均来自固定运行库。
- `SeekProbe` 用真实 libmpv 与解码器，软件渲染到 320×180 内存缓冲，声音送入 null 输出。主线程持有 core，渲染线程通过条件变量接收回调通知，资源按停止、线程回收、render context、core 的顺序退出。
- 测量先确认暂停并消耗在途帧，再记录定位前基线；必须分别在暂停定位和恢复两个阶段出现新媒体帧。REDRAW/REPEAT 不计入新帧。`time-pos` 改变、`seeking=false` 或收到 `PLAYBACK_RESTART` 均不能单独判定成功。

实验未修改正式依赖缓存；媒体与运行库只存于 `.build/`。源码修正遵循原文件 LGPL-2.1-or-later，版权和许可随源码包保留。此构建是实验解封装组件，不能当作完整发行运行库或直接覆盖现有依赖。

候选 TS 和 MP4 共 6 次补充检查都恢复新帧。3 个 TS 定位误差均小于 1/30 秒，未开启全片缓存。这里是每个目标一次测量，时间包含事件轮询精度；不属于统计性能基线，也没有测量整个应用的内存、GPU、物理出光或首声延迟。结果不能覆盖任意大小、超长 GOP 或其他 I/O 条件下的开销。

补充检查的原始命令、媒体身份和逐次结果保留在 `large-file/report.json`。生成使用已验证的 `window-stress-1080p.mp4`，命令为 `ffmpeg -i <MP4> -map 0 -c copy <TS>`；再分别用工具生成的 `seek-probe-pinned` 和 `seek-probe-candidate` 执行 `FILE SECONDS video`，判定与 8 组主实验相同。

## 排除的方案

完整缓存 6 秒短片时，原版内核也能通过，因为它直接使用缓存中的已知关键帧，未走错误的低层定位。限定前读 10 秒、前向缓存 2 MiB、后向 1 MiB 时，长片跳至缓存外的 123 秒仍落到 126.805 秒。mpv 的[缓存说明](https://mpv.io/manual/stable/#options-demuxer-seekable-cache)也明确区分缓存内与缓存外定位。因此没有给正式播放器添加全文件缓存、固定回退秒数或隐式重新打开策略。

## 交错操作补充验证

`verify-seek-lifecycle.py` 复用已核验的运行库和素材，在独立进程中执行同一播放会话的状态交错。新证据见 [seek-lifecycle-validation-2026-10-13.json](seek-lifecycle-validation-2026-10-13.json)，真实链路见 [flow.md](flow.md#候选内核的交错操作与释放)。

| 检查 | 候选结果 | 原版对照 |
| --- | --- | --- |
| 短 TS、长 TS、MP4 各连续前后定位 4 次 | 3 组均通过，每次暂停定位与恢复都有新帧 | MP4 通过；短 TS 无新帧，长 TS 落到后一个关键帧 |
| 每组随后快速提交 100 条定位命令 | 全部回复，最终停在 3 秒附近，暂停意图保留，恢复后继续出帧 | MP4 通过；TS 的最终位置或新帧不满足条件，超时失败 |
| 定位请求后立即替换文件 | 新文件身份、从头播放位置与后续新帧均通过 | MP4 对照通过 |
| 定位请求后立即停止 | 视频输出关闭，稳定后一秒内媒体帧计数不增长 | MP4 对照通过 |
| 加载排队后立即关闭，独立重复 10 次 | 10/10，销毁 API 返回并回收渲染线程 | 10/10 |

原版的崩溃、任意失败或报告缺失不能算作“复现已知缺陷”。汇总额外核对原版短 TS 在有效视频输出下出现音频时钟前进但帧数不变的实际记录。新工具的 11 项判定行为测试和原有测试合计 **44 项通过**；修改后的 probe 又重跑了原有 8 组单次定位候选用例，全部通过。C 编译使用 `-Wall -Wextra -Werror`。

这些操作验证 libmpv 队列交错，不验证 `PlayerModel` 的 request ID 过滤，也没有断言替换或关闭恰好发生在某条解码指令执行中。释放记录说明线程已回收、销毁函数已返回，不属于完整泄漏分析。软件帧与 null 音频输出仍不能替代应用 OpenGL 画面和真实声音。

运行库能力核对同时确认：两者都登记了 359 个解封装器，但精简候选关闭了全部封装器，输入协议从 33 种减至 26 种，其中缺少 HTTPS/TLS 等协议。解封装器名称相同也不能证明各格式内部功能完全等价。这是实验配置差异，既未改变当前 Bomu 的能力，也未引入网络功能；正式接入仍需明确完整的运行库配置与来源，不能直接把实验库覆盖到固定缓存。
