# Playback history storage

## Boundary and ownership

`PlaybackState` remains the authority for the active request and live playback snapshot. `PlaybackHistoryStore` is the authority for durable resume preferences and owns the SQLite connection and schema migrations. The SwiftUI feature submits playback events and user commands; it does not hold a database handle or depend on GRDB.

Durable identity is the mounted volume UUID and filesystem resource identifier, with a metadata revision and bounded SHA-256 content samples that invalidate a checkpoint when the resource is rewritten. The path relative to the volume is location metadata and updates after a rename; a volume name is a display label. The original media remains read-only and is never copied. See [media identity](../library/media-identity.md) for the model, transaction, and migration contract.

## Schema

| Table | Authoritative fields | Query path |
| --- | --- | --- |
| `media_sources` | Stable `volume_id` primary key, mutable display name, update time | Resolve current mounted source |
| `media_files` | Integer row ID, source UUID, volume-scoped file number, compatible serialized resource ID, metadata revision, nullable content fingerprint, volume-relative path, size and modification time | Identity lookup on open/save; path index for later browsing |
| `playback_history` | `media_file_id` primary/foreign key, nonnegative `position`, optional audio/subtitle track IDs, `volume` from 0 to 100, `updated_at` | One checkpoint lookup and atomic upsert per resolved file |
| `playback_history_legacy` | Original v0.0 canonical path primary key and checkpoint values | Exact-path migration on first access after upgrade |
| `legacy_history_purges` | Volume UUID and relative directory primary key | Prevent deferred legacy restoration after a privacy rule was removed; not a restriction on new checkpoints |

The source and file rows retain location metadata needed by library browsing, while a composite source/path index supports location queries. Position and volume have both Swift validation and SQLite checks. Resolving identity, updating metadata, migrating any exact-path legacy record, and writing a checkpoint each occur in a GRDB `DatabaseQueue.write` transaction. Renames preserve the row; a changed metadata revision or known content fingerprint clears its prior checkpoint atomically. Existing rows receive fingerprints lazily after the additive `mediaContentFingerprint` migration. The later `completeSmallFileFingerprint` migration preserves the prior 16–80 KiB prefix digest in a compatibility column while normal access establishes a full digest without discarding unchanged-file records; [identity upgrade](../library/media-identity.md#small-file-fingerprint-upgrade) documents the boundary.

## Lifecycle

The application opens its database in `~/Library/Application Support/Bomu/playback.sqlite` before accepting media. If the store cannot be created or migrated, the library shows its unavailable state while direct local playback remains available without checkpoint storage; it does not replace or clear the failed database. See [storage failure recovery](../library/storage-failure-recovery.md). Opening a file with an available store loads its record asynchronously; the player checks the request ID after the read so a slow result cannot replace a newer file. Saved volume is applied before opening, the validated resume position is passed in the native open options, and saved track IDs are applied after the native loaded event.

While a file is active, the player writes the latest native snapshot every five seconds. It also captures the current snapshot when replacing a file, stopping, reaching natural end, or terminating. Termination awaits the final write before releasing the playback engine. SQLite work stays behind the store actor and never runs from SwiftUI view evaluation. One hostless test verifies a periodic checkpoint during playback; a shutdown/resume test then checks the final snapshot in a fresh store and starts a separate XCTest process to verify that position, tracks, and volume survived.

After changing resume startup to pass the validated position to libmpv's `loadfile` start option, Xcode 27 native runs on 2026-10-15 passed both `testSavedAudioTrackAndPositionRestoreInNewNativeSession` and the first-snapshot assertion in `testRealPlaybackPauseSeekReplaceAndRelease`. The tests used a single host window and confirmed audio-track plus position restoration across fresh engines. A fresh visible-app check is still required to close the previously observed frame/timecode mismatch.

If the final checkpoint fails, shutdown still proceeds and releases the native engine; the failure remains available through the persistence error state. The main window presents localized messages that distinguish an unreadable checkpoint (open from the beginning) from a failed save (recent progress may be unavailable next time), without exposing SQLite statements as user instructions. The shutdown path records this state before exiting; it does not promise an alert will remain visible after termination.

On 2026-10-19, the hostless regression held a real write transaction on a second connection to a temporary on-disk database. The player's final checkpoint failed, the recording engine received one shutdown call, and the previously committed position, tracks, and volume remained intact. Opening again while the lock was held reported the restore failure and still submitted the media to the engine. After releasing the lock, a final checkpoint saved successfully and cleared the error. This verifies SQLite contention and model error handling. A separate real-file regression now verifies read-only startup rejection and checkpoint recovery after process exit and restoration of database/WAL/SHM permissions; corrupt database startup also preserves the original bytes. See [storage failure recovery](../library/storage-failure-recovery.md). Disk-full failures, permissions changing during active playback, and native alert presentation remain unverified. The injected-store regression also checks that shutdown attempts its final checkpoint exactly once.

The separate-process checkpoint regression now requires the child to return the actual stored position, tracks, and volume in a temporary result file, in addition to a successful exit status. A test-selection mistake that executes zero child tests therefore cannot count as a successful persistence check. Temporary databases, logs, and result files are removed after each test.

On 2026-10-19, the single-window native run encountered a preexisting duplicate volume/file-number identity for bundled fixtures. The resolver correctly preserved the rows rather than selecting one; library snapshots now suppress conflicting progress, and the player reports the conflict once, opens from the beginning, and suppresses progress writes for that request. A real SQLite regression verifies that Continue Watching omits the item while independent favorites remain visible. A focused model regression verifies the open options and zero save attempts, and the visible run showed a changing frame with no second alert. No conflict-repair transaction was applied and the original media remained untouched; safe user-directed conflict resolution remains a separate design decision.

## Migration and dependency policy

Migrations have stable identifiers and are append-only after release. GRDB is resolved to 7.11.1 and its exact source revision is recorded in `Config/Dependencies.lock.json` and `Bomu.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`. Build and test scripts use the repository-local SwiftPM checkout cache. `scripts/dependencies.py check` rejects a missing or mismatched package pin. The dependency's MIT notice is retained in `ThirdParty/GRDB-LICENSE.txt`.

The migration interruption regression starts from the original path-keyed schema, injects a conflicting table so `mediaFileIdentity` fails after its first table rename, then verifies the rename and checkpoint both rolled back. Removing the conflict lets the same database migrate successfully and restores its saved position and track IDs. This tests failed-migration rollback and retry against the locked GRDB version; it does not replace backups or a process-kill test across every published schema.

Backup recovery is exercised separately through the versioned library archive: one store exports a checkpoint and library preferences, then a newly created database indexes the same unchanged local media and imports that archive. Version 2 archives carry the sampled fingerprint and require it when matching; legacy version 1 archives remain readable using their earlier metadata-only rules. The test verifies identity matching, restored progress/tracks/volume/favorites/category/settings and unchanged source bytes. The archive contains metadata only and cannot restore media that is unavailable or whose identity no longer matches.

## Current limits

Track IDs are persisted and restored through the native adapter, and B05 now exposes selection from the current file's native track list. The app-host suite has run in one ordinary window: 10/10 native integration tests passed, including switching between two real libmpv audio tracks and restoring the selected track plus playback position in a new native session. A hostless shutdown regression now verifies the persisted checkpoint from a separate XCTest process; exact first-frame restore error after an actual app relaunch and database-alert presentation still need dedicated native evidence. If a file's track layout changes, libmpv may reject a stale ID; playback remains active and the selected track is not considered confirmed until the native snapshot reports it. Filesystems without a stable volume UUID or resource metadata produce an explicit checkpoint error; playback continues. Legacy records can only be matched to a file that still exists at its exact old canonical path when first opened.

On 2026-10-19, visible paused seek moved a silent fixture from 14.200 s to 4.200 s and retained Play as the available action; the embedded frame timecode matched 4.200 s. After resuming, browsing Library, and returning, the paused snapshot and embedded frame both showed 10.433 s. The app was then quit and relaunched from the same canonical bundle; reopening the fixture reached its normal end before the next observation. This restart attempt does not measure the first restored frame or establish the under-two-second resume error target.

A second same-day relaunch used a separate silent fixture paused at 9.133 s, with matching embedded timecode. After quitting, reopening the canonical bundle, and selecting that file, the next captured frame showed 14.167 s. The desktop action took about five seconds to return even when the screenshot preceded the accessibility read, so this observation cannot isolate the first rendered frame or establish the resume-error target. The test window was closed and the disposable 3.25 MB fixture removed. Further first-frame acceptance needs an observation method that measures the initial presentation rather than repeating this delayed capture.

## Explicit history clearing

`clearAll()` deletes both identity-backed checkpoints and deferred exact-path legacy checkpoints in the same write transaction. It leaves source/file identities, membership, favorites, categories, and privacy rules intact. A failed legacy delete rolls back the current-table delete as well. This prevents an upgrade-era row from migrating back after the user cleared history. The 2026-10-19 regression reproduced resurrection before the fix and verifies persistence after reopening, failure rollback, and successful retry afterward.

Settings routes this action through `MediaLibraryRecordOperations.clearHistory()`. That operation drains scans and preference writes, delegates checkpoint draining/suppression to `PlayerModel`, then refreshes the visible library on either outcome. PlayerModel throws clear failures rather than silently treating them as success; Settings owns their presentation. The existing current-session history-suppression tests still pass.


## Privacy during deferred migration

The additive `legacyHistoryPrivacyPurges` migration retains the deletion scope of active private-folder rules independently of their future-recording policy. File access validates real volume/path identity before restoring a legacy checkpoint, consumes excluded old rows, and still allows new saves after privacy is disabled. Import, manual exclusion and migration share the same indexed purge operation. The scopes disappear after the last legacy row is consumed or all history/library records are cleared. They are local migration state and are not part of the archive format. Transaction rollback, upgrade compatibility and evidence are documented in [deferred legacy privacy deletion](../library/archive-import.md#deferred-legacy-privacy-deletion).
