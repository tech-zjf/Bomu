# 迁移前备份与恢复

实现于 2026-10-24。适用当前本地 SQLite 数据层；不等同于发行版本迁移矩阵或完整恢复 UI 验收。

## 归属与顺序

`PlaybackHistoryStore.init` 打开唯一 WAL 连接 → `DatabaseMigrationBackup.migrate` 检查 schema → 必要时用 GRDB / SQLite backup API 复制一致快照 → `quick_check` → 关闭目标连接 → 同目录原子移动为正式快照 → 执行 migrator → 成功后保留最近两份。

空库首次建表及 schema 已一致时不创建备份；内存数据库不落盘。若库含本版本未知迁移，明确拒绝打开，不尝试降级。备份不能建立、不能验证或已有恢复点损坏时，停止升级并将错误交给既有资料库不可用界面；不会删除主库或静默重建。实际迁移失败保留主库与备份，已提交的早期迁移可能仍在主库中。

## 文件与保留

应用路径为 `~/Library/Application Support/Bomu/playback.sqlite.migration-backups/`。目录权限 0700，快照 0600。文件名是目标迁移序列的 SHA-256 摘要；同一个目标版本失败重试时复用并验证最初的快照，避免把部分迁移后的状态覆盖到原始恢复点。新目标升级成功后仅裁剪符合应用快照命名规则的普通文件，按修改时间保留最近两份；不会把手工恢复副本当作自动快照删除。失败升级不裁剪已有恢复点。

写入使用唯一 `.partial` 暂存文件，成功后移动为独立 `.sqlite`，目标切回 DELETE journal 并关闭，因此不需要配套 WAL/SHM。普通异常退出清理本次暂存及 sidecar；进程被强杀留下的 `.partial` 不当作可恢复备份。恢复前应忽略这些不完整文件。

自动副本包含当时的本地用户事实。清除历史、清除资料库、启用隐私目录，或者导入带隐私规则的归档时，先移除自动备份，再修改活动记录；删除副本失败则报告失败，不宣称隐私清理完成。升级后发现已有隐私规则也清除快照，防止旧版本残余历史被恢复。隐私清理会主动缩短恢复窗口；不会删除用户自己导出的归档。

## 手工恢复流程（尚无自动替换 UI）

1. 退出 Bomu，确认没有进程持有待恢复数据库。不要在 WAL 连接仍活动时替换主文件。
2. 完整保留当前主库、WAL/SHM 及 migration-backups 目录，供故障定位与回退；不要先删除故障现场。
3. 选取正式 `.sqlite` 恢复点，在独立路径打开并运行 SQLite 完整性检查、核对 `grdb_migrations` 和所需用户记录。文件名只标识目标序列，不能替代内容验证。
4. 在隔离目录或独立用户环境中验证它可被对应兼容版本打开；需要重新升级时保留原备份。再由用户明确决定是否替换活动数据。替换时将旧主库及其 sidecar 一并移开，不能混用旧 WAL 与恢复主库。

本轮测试已把含 WAL 提交的快照复制到独立路径，验证可读与升级前内容一致；另外注入迁移失败和备份目标故障，验证没有覆盖初始恢复点或越过备份失败继续迁移。四次升级的保留回归还在备份目录放置较旧的手工 `.sqlite` 副本，确认它不被自动裁剪，而应用快照仍只保留两份。公开 beta 前仍需用户可操作的恢复入口、各公开版本升级矩阵、磁盘写满/强杀与最终发行包演练。
