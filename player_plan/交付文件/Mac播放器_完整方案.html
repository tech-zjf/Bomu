Mac 开源播放器产品与技术方案

研究日期 2026 年 10 月 12 日 · 文档版本 1.0

建议开工做一个有明确边界的验证版本。用成熟播放内核保证基础能力，把差异落到随手打开、目录与收藏共存，以及可预览撤销的个性化交互。

1 项目判断与实施决策

结论：值得做一个限定范围的 Mac 开源播放器，先验证用户是否愿意持续使用，再决定长期投入。项目的成立条件是把漂亮的媒体库、直接打开文件的效率和可定制的播放交互结合好。单靠 Apple TV 外观、免费开源或广泛格式支持，吸引力不够持久。

确定范围：只做 macOS；视觉参考 Mac 版 Apple TV App；处理普通本地视频和后续加入的标准网络流；通过官网和 GitHub Releases 下载；不以商业收入和 App Store 上架为目标。H.265 是常规编码支持的一部分。

建议先投入 2 周验证播放与渲染，再用约 6 至 8 周做出可公开试用的 v0.2。熟悉 Swift 和原生 Mac 开发的一人团队，完整 v1.0 的规划量约 22 至 28 个全职工作周，包含约 30% 返工和兼容性缓冲。时间是规划估算，不能用来承诺发布日期。

1.1 必须成立的三个用户价值

随手打开：Finder 双击、拖入文件、拖入文件夹都能立即播放，不要求先建立媒体库，也不弹出多步引导。

认真收藏：用户愿意添加目录时，同一批文件可以按原目录或电影与剧集浏览；离线硬盘保留目录和进度，重新连接后恢复。

轻度可玩：观影界面保持克制；字幕、快捷键、控件位置和播放方案可调，设置可预览、撤销、导出和分享。

1.2 为什么新应用而不是继续做插件

IINA 插件已经能控制播放、访问 mpv、提供侧栏和视频覆盖层。因此，只做双字幕、快捷键、截图、书签或滤镜，优先给现有项目贡献插件会更划算。[S02]

独立应用的理由是统一设计媒体库、文件夹浏览、播放窗口和返回路径。这些改变涉及应用主导航、持久化模型、窗口生命周期和播放器状态，超出了一个小插件的合理边界。建议新建薄应用外壳，复用播放内核；先不 fork 并长期维护整个 IINA 或 VLC。

1.3 继续与收缩的条件

2 市场调研与具体差异

调研日期为 2026 年 10 月 12 日。检索覆盖主流 Mac 播放器、原生开源项目、官方发布记录、开发接口和公开用户讨论。产品功能比较依据官方资料；“用户为什么迁移”和“本项目能否更顺手”属于需要后续任务测试验证的假设。新项目的 README 和宣传页能证明已有相似方向，不能证明其稳定性或用户规模。

2.3 用户反馈给出的线索

VidHub 应用页可见用户要求更合理的海报密度、Mac 原生感、更多媒体信息和批量已观看操作。这支持“信息密度与管理效率值得验证”，不代表所有用户都不满意。[S06]

Infuse 论坛中有用户希望在服务器内容之外继续保留原有文件夹结构。应允许用户在目录和整理后的视图间来回切换。[S14]

IINA 的 HDR 问题汇总说明颜色和显示器切换需要专门验证；历史问题不能直接作为当前版本仍有故障的证据。[S15]

公开讨论中既有只想用文件夹管理的用户，也有重视原生外观的用户。产品应允许轻量打开，而不是强制整理所有内容。[S17]

2.4 本项目的具体差异化承诺

拟做的体验具体行为与市场的关系验证方式
播放器和收藏库共存双击文件直播放；加入收藏后使用同一播放器；返回原目录和原滚动位置各家有部分能力，本项目验证完整路径的一致性5 个任务对比完成时间、误操作和偏好
目录与内容两种视图在原文件夹与电影剧集视图间切换，保持选中项和进度Owl 擅长目录，Infuse 擅长内容整理；我们连接两个视角跨视图找回同一文件，最多 2 次操作
可调的信息密度舒适与紧凑布局、海报大小、原文件名显示独立切换可调布局已有竞争，需要做得可发现且一致小屏与大屏对比，用户不靠猜即可调整
可分享的播放方案字幕、倍速、控件、快捷键分开成方案；一键预览和撤销IINA 已有插件与配置；我们的差异是假设中的低门槛组合新用户 60 秒内应用并恢复默认

这些组合差异可以吸引偏好 Mac 原生体验和本地收藏的用户，但易被复制。长期优势将来自细节一致、缺陷响应、兼容性样本和社区贡献，而不是一种语言或一张主界面截图。

2.5 产品表达和获取首批用户

推荐对外表达：一款给 Mac 本地视频使用的开源播放器，可以随手打开，也可以认真收藏。功能说明以可演示的行为为依据，避免“所有格式”和“画质超过所有播放器”的承诺。

官网首屏展示一段约 30 秒的真实操作录像：Finder 打开 MKV → 返回收藏库 → 切到原文件夹 → 恢复进度 → 调整双字幕 → 还原默认。首页的主要动作是下载，旁边是源码、系统要求和版本记录。Mole 可作为网站与开源发布路径的参考，不照搬其终端安装方式。[S31]

先邀请 12 至 20 位已有 IINA 或 Infuse 使用习惯的 Mac 用户自愿试用，记录失败路径和迁移原因。待核心体验成立后，再发布到 V2EX、相关社区和 GitHub。方案不包含代用户发帖、创建账号或发布软件的动作。

3 产品需求文档

3.1 用户与目标场景

用户当前行为我们优先解决的任务
随手看视频的人从 Finder、下载目录或外接硬盘打开单个视频立即看、暂停、拖动、切字幕、下次继续
本地收藏用户文件夹里有电影、剧集与个人视频保留原目录，同时有清晰的封面、进度和检索
喜欢调节体验的人经常调整字幕、倍速、快捷键或窗口设置能被发现、预览、撤销并复用

优先顺序为播放可靠性、打开与返回路径、目录和收藏浏览、轻度定制、网络输入。音乐库、剪辑工具、云盘聚合和多设备同步不进入首个稳定版。

3.2 范围和版本边界

首个公开体验版 v0.2 必须具备本地文件与目录播放、单窗口导航、Apple TV 风格首页、原目录视图、继续观看、搜索、字幕音轨和签名公证后的直接下载。电影自动匹配、进阶定制和标准网络流后续加入。

v1.0 目标为个人 Mac 上的可靠本地播放器和小型媒体库，兼容经验证的主要视频、声音与字幕格式，并提供标准 HTTP/HLS/DASH 网络输入。不做跨平台、账号体系、内容商店、服务器端转码、自动下载站解析、蓝光菜单和大型脚本插件平台。

应用只读引用用户媒体，索引、封面和进度写入自己的数据目录。“从媒体库移除”只移除引用。首版不提供原视频删除、移动或重命名能力。

3.3 信息架构

主窗口
  首页：继续观看 / 最近加入 / 固定的目录或收藏
  视频：全部内容 / 电影 / 剧集 / 个人视频
  文件夹：用户添加的目录，保留原层级
  收藏：手工列表和收藏项
  搜索：文件名 / 手工标题 / 已缓存的作品标题
  底部当前播放栏：返回播放 / 暂停 / 下一项

  主画面 + 临时控制浮层
  按需打开：播放队列 / 音轨字幕 / 画面与声音设置
  返回：保留浏览视图、滚动位置和选中项

设置
  常规 / 外观 / 播放 / 字幕 / 快捷键 / 数据 / 更新

3.4 关键用户流程

首次打开：窗口显示“打开视频”和“添加文件夹”；不要求账号或网络。打开文件后直接进入播放，媒体库稍后再建。

Finder 双击：应用冷启动或已运行都能接收文件。默认沿用当前播放窗口；连续收到多文件时只改变队列一次，不反复抢焦点。

添加目录：选择后立即展示已发现的文件名，封面和信息渐进补齐；扫描可取消；添加目录不复制原视频。

浏览与播放：浏览单击选中，双击播放；卡片上明确的播放按钮也可直接播放。详情入口与播放入口分开，避免每次都强制经过详情。

返回浏览：按返回按钮或 Esc 退出播放器的沉浸页面，播放器继续或暂停由用户设置决定；默认继续播放并显示当前播放栏。回到进入前的目录与滚动位置。

继续观看：点击进度卡从保存位置开始；卡片菜单可“从头播放”和“标为已看”。短视频与长视频使用不同的完成判断，但用户可以覆盖结果。

硬盘离线：卡片变为不可播放状态而非消失；点击说明来源离线，并提供重新定位目录。重新接入后自动核对，不重复添加内容。

3.5 UI 还原与交互规格

视觉方向为 Mac 版 Apple TV 的侧栏、内容分组、海报与横幅、克制的层级和播放浮层。界面有自己的名称、图标和用户内容。开始设计时固定 macOS 与 Apple TV App 版本，采集 960×640、1280×800、1440×900 三组参考窗口；这才是后续像素对照的基准。

项目初始设计规格验收
布局侧栏初值 220 pt，可收起；内容边距 24 至 40 pt；最小窗口 900×600连续缩放无重叠、裁切或横向溢出；紧凑窗口可收侧栏
卡片电影海报 2:3；普通视频与继续观看 16:9；缺图使用本地帧和清晰标题不同来源不会被拉伸；无网络也有可读卡片

播放浮层鼠标静止约 2.5 秒隐藏；聚焦控件、菜单展开或拖动中保持可见退出拖动立即同步状态；不会误隐藏正在操作的控件

系统外观明暗模式；系统材质；macOS 26 增强效果可选macOS 14/15 使用稳定替代材质，减少透明度时可读

上表数值是待原型测试调整的设计初值，不是对 Apple TV 内部设计参数的测量结论。“1:1”应体现在参考基准、组件和交互的逐项核对，不能只靠堆叠玻璃效果。

3.7 设置作用范围

播放设置有四个层级：应用默认、用户方案、单文件记忆、当前会话临时调整。界面显示正在修改的层级；临时调整不会悄悄修改默认。字幕轨道与偏移默认按文件保存；目录的排序与密度按视图保存；音量为全局设置且切文件不突然重置。

v0.4 的可玩性限定为颜色主题参数、布局参数、快捷键、字幕与播放方案、书签和循环。导入方案前展示变更摘要；应用后可撤销到导入前快照。首版不运行外部脚本。

3.8 非功能需求

所有性能数值都是拟定验收目标。基准设备为 M1 8 GB 与一台较新 Apple Silicon Mac；覆盖 macOS 14、15、26 可获得的真机或测试环境。缺少的设备组合不能标记为已验证。

3.9 小规模用户验证

用同一组普通文件在现用播放器和原型完成五个任务：打开 MKV；找到并继续昨天的视频；在目录与海报之间找回同一文件；调整字幕并恢复；播放中返回浏览再继续。记录完成率、时间、错误次数和理由，不要求用户先夸外观。

成功假设：12 人中至少 8 人不经指导完成任务；至少 6 人愿意把原型用于接下来两周；至少 5 人能主动说出一个稳定的交互优势。若用户只是觉得截图好看，核心差异尚未成立。用户研究数据由用户主动提交，不默认收集使用事件。

4.3 播放接口

protocol PlaybackEngine {
    func open(_ request: OpenRequest) async throws
    func play() async throws
    func pause() async throws
    func seek(to seconds: Double, mode: SeekMode) async throws
    func selectAudio(_ id: TrackID) async throws
    func selectSubtitle(_ id: TrackID?) async throws
    func setRate(_ rate: Double) async throws
    func stop() async
    var events: AsyncStream<PlaybackEvent> { get }
    var capabilities: PlaybackCapabilities { get }
}

OpenRequest：requestID、source、resumeAt、selectedTracks、profile
PlaybackEvent：loading、ready、position、buffering、tracksChanged、ended、failed
PlaybackCapabilities：seek、live、dualSubtitle、HDRMode、hardwareDecode

接口示意以职责为准。实现时 RenderSurface 单独管理平台资源，不要求它跨 actor 传递。每次打开生成 requestID；晚到的旧请求事件必须丢弃。定位请求合并，只保留用户最近一次意图。任何失败都返回可解释的错误分类和恢复动作。

4.4 状态机与生命周期

idle → opening → ready → playing ⇄ paused
                  │          │
                  └→ failed  ├→ buffering → playing / failed
                             ├→ seeking → playing / paused
                             └→ ended → next / idle

新 open 请求：取消旧准备流程，保留新 requestID
用户 stop：保存当前进度，停止输出，再释放媒体资源
切换全屏或返回媒体库：只改变呈现，不重建播放内核
退出应用：停止事件投递 → 释放渲染上下文 → 销毁内核

playing 与 paused 是用户意图；buffering、seeking 是暂态，不能把网络恢复后的播放状态猜成自动播放。保存队列索引与当前文件 ID，结束事件需识别自然结束、用户停止和加载失败，防止误跳下一集。

4.5 线程和渲染的约束

内核控制与事件消费使用独立串行执行域；C 回调只唤醒事件泵，不直接改 SwiftUI，不在回调中同步等待 UI。Swift actor 不保证固定 OS 线程，不能仅靠 actor 就假设 OpenGL context 始终在正确线程。

渲染使用专用执行域，遵守 context current 与 mpv 渲染线程要求；控制线程与渲染线程之间避免相互等待。mpv 的文档明确提示相关 API 混用可能产生死锁。[S19][S20]

UI 位置更新合并到约 10 Hz，画面渲染按内核帧更新处理；拖动时本地时间显示实时响应，释放后发最终精确定位。不要每帧转成 SwiftUI Image，不通过主线程拷贝全分辨率 RGBA。

NSViewRepresentable 包装一个生命周期稳定的 AppKit 视频宿主。主播放页和当前播放栏之间迁移同一个宿主视图或改变它的布局，确保任一时刻只有一个父视图和一个有效渲染上下文。SwiftUI 重算不能隐式创建第二个 mpv 实例。最小化、锁屏和屏幕变化分别测试。

4.6 HDR 颜色与原画质

原文件保持只读，正常播放只有解码与显示，不执行重新编码。“不改原文件”不等于“显示颜色必然正确”：色彩空间、全幅与限幅、显示器 ICC、HDR 与 SDR 映射都需要验证。

v0.0 先确保 SDR 的 H.264/H.265 在内置与外接显示器上的范围、灰阶和色彩正确。v0.1 的确定承诺是 SDR；HDR 输入只有经验证的 SDR 映射路径才列为支持，未通过就如实显示限制。真正的 EDR/HDR 输出不作为早期 UI 版本的前置卖点。

同时比较当前 IINA 与 QuickTime 对兼容样片的呈现，使用标准测试图和硬件信息解释差异。主观截图不能证明 HDR 正确，系统截图本身也可能经过映射。[S15]

若原生 HDR 是用户验证后的高优先级需求，单独开 2 至 4 周验证 AVFoundation 路径或另一渲染内核。保持 PlaybackEngine 接口，但不在首版同时维护多个自动切换内核。切换内核可能改变字幕、轨道、截图和进度行为，需要完整兼容测试。

4.8 扫描与离线恢复

扫描分三步：枚举可见文件；读取快速基础属性；按用户可见性和最近播放优先探测、生成缩略图。首屏先出现文件名与占位图。遍历不跟随无限符号链接，去重嵌套来源，限制并发。

本地目录用文件事件触发去抖后的增量核对；事件丢失、目录变更或挂载变化时做局部或完整对账。只有来源在线、权限有效、扫描完整成功时，才能把本轮未发现项标为 missing。取消、超时、权限错误和磁盘断开都不能触发批量清理。

在应用重启时解析保存的目录 bookmark，检查失效并引导重新定位。非 App Store 分发也仍要尊重文件访问权限与系统隐私限制，不要求用户授予整个磁盘访问权。将书签访问与来源生命周期绑定，避免泄漏授权句柄。

4.9 缩略图与在线信息

预览进程最多同时两个任务，播放开始时缩减到一个或暂停。每任务有超时和取消；用参数数组启动命令，不拼接 shell 字符串。通过固定可执行路径运行，清理临时文件，回收被取消的子进程。

卡片图优先本地 sidecar 图片，其次已缓存在线海报，再次本地视频抽帧。时间轴预览按需生成，不为每个文件一次生成整条时间轴。缓存 key 包含文件指纹、抽帧时间、尺寸和处理版本；LRU 上限初值 1 GB，可调并可清理。

在线信息默认关闭，由用户对特定目录启用。匹配时只发送用于查询的标题与年份；不上传视频或全路径。先读取本地 NFO 和图片，再做可选 TMDB 匹配；手工选择与修正有最高优先级。服务端故障时使用本地卡片继续播放。

TMDB 接入需要按其规则申请凭据并提供署名；“非商业开源”不等于没有服务使用约束。桌面二进制内的公共 API key 不能当作可保密的服务器凭据；配置可更换并控制请求速率，不把个人私钥放进仓库。[S28]

4.10 网络输入的边界

v0.5 先实现标准 HTTP/HTTPS 文件 URL、HLS、DASH。URL 先分类，凭据保存在 Keychain；日志移除 query token、认证头和用户目录。网络模式与本地模式复用播放界面，但 capability 不同。

VOD 根据真实总时长提供定位；直播没有确定总时长就禁用普通进度条，显示直播和缓存状态。没有 HTTP Range 的资源不能假装可随机定位，也不默认把整部大视频偷偷缓存到磁盘。

HLS/DASH 能打开不代表自动拥有与网页流媒体引擎相同的自适应码率能力。v0.5 明确验证默认变体选择、手动切换、定位和断线行为；没有验证动态 ABR 就不提供误导性的“自动随网速切换”选项。[S21][S32]

SMB 首版通过 Finder 挂载后的目录使用，产品表现为普通文件来源。WebDAV、Jellyfin、Emby、Plex 的浏览和账号接入后置评估；它们不是简单填入播放 URL 就完成的功能。RTSP 等输入也只在有样本和真实需求后追加。

4.11 可玩性和扩展设计

所有内置动作登记到 CommandRegistry：命令 ID、标题、可用条件、快捷键和处理入口共用。菜单、键盘和后续命令面板调用同一动作，避免不同入口的行为漂移。

Profile JSON 有 schemaVersion、明确字段白名单和数值范围。主题只允许颜色、间距密度、圆角与可见控件配置；不得引用外部可执行文件、脚本或任意本地路径。导入提供字段级预览，保存旧快照以撤销。

运行脚本的插件平台至少等 v1.0 用户验证后再决定。若未来要提供文件或网络能力，必须有清楚的权限与隔离设计；JavaScript 放在同一进程运行不自动构成安全隔离。当前版本的可玩性无需承担整个插件生态的维护。

4.12 网站分发与自动更新

推荐路径：静态官网 → GitHub Releases 的签名公证 DMG → 拖入 Applications → 首次打开 → 直接播放。安装包自带播放依赖，普通用户不需要 Homebrew、终端和额外解码包。

不上 App Store 仍建议使用 Developer ID 签名和 Apple 公证。公证属于自动检查，不是 App Store 审核。Apple Developer Program 当前通常为每年 99 美元或当地货币；这是友好分发的维护成本，与收费商业模式无关。[S25][S26]

4.13 开源与依赖管理

建议应用采用 GPL-3.0-or-later，并对实际随包依赖逐项核对兼容性。mpv 默认 GPLv2-or-later，也提供关闭 GPL 的 LGPL 构建方式；实际许可由构建及依赖决定，不能给所有 mpv 包统一贴 MIT 标签。[S22]

每个发布版本保留自身源码、依赖版本与源码快照、补丁、构建脚本、配置参数、第三方许可和 notices。网站链接对应发布版本的源码与构建说明。初版不 fork 播放内核；需要补丁时尽量先提交上游，并将补丁数量保持可控。

支持清单来自随包二进制实际探测结果，加上测试矩阵；不是从 FFmpeg 官网复制一份列表就声称全部支持。更新内核前重跑媒体样本、颜色、字幕、窗口和能耗回归。

6.2 个人开发者维护策略

主线始终可构建，按版本建立小范围任务。每个发布版本有固定媒体样本与五条核心路径。功能请求按可重复任务排序，不按评论声音大小排序。播放问题优先拿到最小样本与系统信息，再判断属于应用、内核还是文件。

按月检查播放依赖更新与已知问题，但不自动追所有上游最新版。依赖升级作为独立改动发布 beta。贡献入口优先欢迎字幕、翻译、兼容样本、键盘辅助和小范围 UI 修复，不把核心渲染交给未经验证的零散补丁。

用户自愿导出诊断包时先展示包含内容，移除路径、文件名和网络 token。社区反馈可用匿名文件 ID 与媒体元信息定位问题。默认不发送遥测；持续使用指标通过主动参与测试取得。

媒体库拖慢播放扫描抽帧导致音画卡顿或 UI 卡顿暂停后台任务，降低并发，限制缓存，按可见内容加载
资料服务不可靠元数据 API 不可用、匹配错误或额度不足默认本地可用；停用在线匹配仍有标题缩略图
直接分发安装困难签名、依赖或公证失败修复发布流程；不把关闭系统保护当成正常安装步骤
维护范围失控同时要求云盘、服务器、插件、投屏和剪辑保留路线图，按验证结果一次做一个方向

6.4 最终建议

开工，但把第一阶段限定为可比较、可放弃的验证。选择 Swift 原生 UI 与成熟播放内核；在 v0.2 交付完整的直接打开、目录浏览、收藏首页和返回路径。只有用户愿意持续使用，才继续投入电影整理、方案分享和网络输入。这个项目有做出鲜明体验的空间，空间来自完成路径和长期打磨，不能只靠 Apple TV 风格复刻。
